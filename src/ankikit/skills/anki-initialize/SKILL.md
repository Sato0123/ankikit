# anki-initialize

**流れ**: スコープ確定 → 方針の仮置き → 棚卸し面談 → カード化 → 要点とノート → 方針の確定 → ブランチでコミット → 承認 → push

デッキの初期化は `/anki-grill` と**目的が違う**。grill は「今日あったこと」を掘るが、initialize は
**まだ何も起きていない状態に骨組みを置く**。だから **このスキルに限り、モデル側が論点と裏面を持ち込む**。
その代わりに歯止めを 2 つ置く:

- カードにするのは**面談で実際にテストした論点だけ**（教科書の目次を丸ごと流し込まない）
- 裏面はモデルが書くが、**1 枚ずつユーザーに正しさを確認させる**

**答えられた論点も捨てない。** 今日答えられたことは半年後には忘れている。ただし新規カードとして入れると、
本当に知らなかったカードと同じ頻度で出てきて復習の枠を食う。だから理解度に応じて `known:` を付け、
**最初から復習済みの状態**で入れる（`known: 3` なら 12 日後に初めて出る）。
記法と初期間隔の表は `decks/README.md` の「既習カード」にある。

承認境界は grill と同じ。**main にマージされるまで Anki には 1 枚も入らない。**

---

## 0. 下ごしらえ（黙ってやる。要約して見せない）

- `decks/README.md` — 記法とコマンド
- `decks/*/README.md` を**全部** — 似た目的のデッキが既にあれば、新設せず**そこに足すこと**を先に提案する
- `uv run ankikit decks` — 未マージのカードが残っていたら、先に片付けるか聞く

---

## 1. スコープの確定

デッキは「**入れる基準が書ける粒度**」でだけ切る。ここが決まらないと以後の全セッションの判断がぶれる。

1 問ずつ聞く。

> 何を覚えたい？ 具体的に。

> なぜ今？ 何をしていて必要になった？

> 3 か月後、何ができていれば「作ってよかった」と言える？

### 粒度の判定

| | 例 | 症状 |
|---|---|---|
| 広すぎ | `プログラミング` `英語` | 入れる基準が「役に立つこと」にしかならない。切り直す |
| ちょうど | `react-rendering` `sre-oncall` `meeting-english` | 入れない基準を具体例で書ける |
| 狭すぎ | `useEffect の依存配列` | 10 枚で尽きる。一段上げる |

決まったら slug（kebab-case）と Anki 上のデッキ名（`親::子`）を提案し、確認を取ってから作る。

```
uv run ankikit new <slug> --anki-deck "親::子"
```

**`new` を先に実行すること。** `ankikit stage` は `decks/<slug>/` が存在しないと失敗する。

---

## 2. 方針を仮置きする

**README をここで全部埋めない。** 問診の軸になる分だけ決める。

- **目的** — 1〜2 文。1 で聞いた「3 か月後」をそのまま使う
- **スコープ外** — 今回は扱わないもの（例: `sre-oncall` なら「Kubernetes の内部実装は扱わない」）

入れる基準・入れない基準は **5 で確定させる**。今書いても、実際に何を捨てたかを知らないまま書くことになり、
「重要なことを入れる」のような使えない基準になる。

---

## 3. 棚卸し面談（このスキルの本体）

**目的は「知らないことの発見」であって、教えることではない。** ここで解説を始めない。

### 進め方

1. スコープから**論点を 15〜25 個立てる**。
   **リストはユーザーに見せない。** 見せると「これは知ってる／知らない」の自己申告になり、
   一番危険な「知っているつもり」が素通りする。
2. **1 問ずつ口頭でテストする。** まとめて 3 つ出さない。
3. 答えを聞いて、**理解度で仕分ける。捨てる箱は無い。**

   | 反応 | 入れ方 |
   |---|---|
   | 「知らない」と即答 | 新規（`known:` なし）。ただしスコープ内かを確認してから |
   | 半分言えた・誤解があった | 新規（`known:` なし）。**誤解の中身を裏面の「なぜ」に書く** |
   | 答えは出たが説明が詰まった | `known: 1`（2 日後に出る） |
   | 少し考えて答えられた | `known: 2`（5 日後） |
   | 即答できた | `known: 3`（12 日後） |
   | 毎日使っていて間違えようがない | `known: 4`（25 日後） |

   **判定を口に出して確かめない。** 「今のは即答でしたね」と言うと以後の回答が演技になる。黙って記録する。

4. **「知ってる」には必ず説明させる。** 用語を言えるのは知っているうちに入らない。
   > じゃあ説明して。3 行で。

### 論点の立て方（ストック）

- **地雷**: この分野を始めた人が最初の 1 か月で必ず踏む間違いは？
- **区別**: 似ていて混同されるペアは？ 何が違う？
- **境界**: それが**使えない**のはどういうときか。例外は？
- **既定値**: 何も指定しないとどうなるか
- **由来**: なぜそういう仕様／語法になっているか
- **手順の落とし穴**: 順番を間違えると壊れるところ
- **本人固有**: ユーザーの環境・仕事で、それが実際に出てくる形は？

**本人固有の論点を必ず混ぜる。** 一般論だけで組むと教科書のコピーになり、思い出すきっかけにならない。

### やめる合図

- **新規**カード候補（答えられなかったもの）が 20 に達した
- **3 問続けて即答された** → 論点が浅い。一段深くするか、スコープ自体を上げる
  （即答分は既習カードとして残るので、掘り直しても取りこぼさない）
- 3 問続けて「まったく知らない」 → 深すぎる。初期化ではなく学習が先。段を下げる
- ユーザーが「もういい」と言った

---

## 4. カード化

面談でテストした論点を、上の表のとおり**新規と既習に分けて**カードにする。

- **表面**はユーザーに出した問いの形をそのまま使う。用語ではなく遭遇する状況の形にする
- **裏面はモデルが書く。これはこのスキルだけの例外。** 一文 ＋ なぜ
- **既習カード（`known:` 付き）の裏面は、ユーザーが口にした説明をそのまま使う。**
  答えられたのだから本人の言葉がある。モデルが教科書の言い方に書き直さない
- 1 カード 1 事実。「かつ」「および」が入ったら分割する
- 枚数: **新規は 10〜20 枚**。既習は面談で答えられた分だけ（数は絞らないが、
  テストしていない論点を既習として水増ししない）

### 裏面の確認（省略しない）

書いた裏面は 1 枚ずつ見せて、その場で判定させる。

> これで合ってる？ 違ってたら直して。

- ユーザーが自分の環境の言葉で言い直したら、**その言い方を採用する**
- **ユーザーが「正しいか判断できない」と言ったカードは作らない。** 正しさを確認できないカードは毒で、
  間違ったまま何か月も復習することになる。捨てるか、調べてから次のセッションに回す

### 書く場所

`decks/<slug>/cards/<YYYY-MM-DD>.md`。ファイル冒頭のフロントマターに出所を残す:

```markdown
---
tags: [seed]
---

## TIME_WAIT が 2MSL 待つのはなぜ？
A: 遅れて届いた重複セグメントが次の接続に混ざらないため。
known: 3

## SO_REUSEADDR を付けると何が変わる？
A: TIME_WAIT 中のポートに bind できる。接続の同一性は保証されないので、待つ理由自体は消えない。
```

初期化で入れたカードだけを Anki 側で後から絞り込める（日々の grill のカードと区別がつく）。

番号付きで表面と裏面をそのまま見せ、**既習のものは `known:` の値も添える**。長い解説は要らない。

---

## 4.5 要点とノートを書く（省略しない）

カードは 1 枚 1 事実なので、**単元としての筋が残らない**。半年後に README を開いて
「ああこの単元ね」と思い出せるように、散文でも残す。

- **`decks/<slug>/notes/<YYYY-MM-DD>-<topic>.md`** — 面談で出てきた話の筋を散文で。
  カードにしなかった背景・図・具体例はここに置く。Anki には送られない
- **README の `## 要点`** — 5〜10 行。この単元の骨格だけ。詳しくはノートに任せる

ノートは**面談で実際に出た話だけ**で書く。ユーザーが一度も口にしていない解説を足さない
（それは教科書であって、この人の記憶の手がかりではない）。

---

## 5. 方針を確定させる

ここまでで「実際に何が弱かったか」が分かっている。`decks/<slug>/README.md` を書き切る。

- **入れる基準 / 入れない基準は、このセッションで実際に拾った例・捨てた例を引いて書く。**
  - 悪い: 「重要なことを入れる」
  - 良い: 「実際に手が止まった問いは新規、口頭で答えられた問いは `known:` 付きで入れる。
    面談でテストしていない一般論は入れない（今日 3 問そうやって外した）」
- **`## 前提（既に押さえていること）` を足して、3 で答えられた論点を箇条書きで残す。**
  以後の `/anki-grill` がこれを読み、**同じことを二度と聞かない**。
  ただし**カードとしては既習で入っている**ので、忘れたころに Anki が出してくる。
- **`## 要点`** は 4.5 で書いたものを置く
- **運用メモ**: 1 日の新規枚数の目安、次に掘る予定の領域

フロントマター（`anki_deck` / `note_type` / `tags`）は `ankikit new` が入れた値のままでよい。触るなら
`decks/README.md` の記法に従う。

---

## 6. ブランチでコミット

```
uv run ankikit stage <slug>      # staging/<slug> に切り替え（無ければ main から作る）
uv run ankikit lint --deck <slug>
```

エラー 0 件を確認してから、**方針とカードを分けて**コミットする（`decks/` 配下だけを add する）:

```
git add decks/<slug>/README.md decks/<slug>/notes && git commit -m "deck(<slug>): 方針と要点"
git add decks/<slug>/cards && git commit -m "cards(<slug>): <YYYY-MM-DD> 新規N枚 + 既習M枚"
```

分けておくと、承認時に「方針」と「カード」を別々に確認できる。

---

## 7. 承認（main へマージ）

```
git diff main...HEAD -- decks/
```

> `staging/<slug>` に方針と 新規 N 枚 + 既習 M 枚 をコミットした。main にマージすると Anki に入る。マージしていい？

**明示的に承認されるまでマージしない。** 「この枚は要らない」と言われたら、ブランチ上で消してコミットし直し、
もう一度聞く。承認されたら:

```
uv run ankikit approve <slug>
```

---

## 8. push

```
uv run ankikit push --deck <slug>
uv run ankikit status <slug> --write   # README の学習状況ブロックを埋める
```

- 「追加 N / 更新 M / うち既習 K」の行をそのまま報告する
- **既習の枚数が 0 なら `known:` を書き忘れている。** 面談で答えられた論点があったなら、
  カードファイルを直してコミットし直す
- 「追加 0」ならまだマージされていない。`uv run ankikit pending` で確認する
- Anki が起動していなければ、**カードは main にマージ済みで無事**だと伝え、
  「Anki を起動して `uv run ankikit push` を実行すれば入る」と案内する。ここで巻き戻さない
- ノートタイプ名で失敗したら `uv run ankikit doctor` の結果を見せる

最後は 2〜3 行。デッキ名、枚数、次に掘ると良さそうな領域。総括は要らない。

---

## やらないこと

- スコープを決めずに論点を出す
- **論点リストを見せて「知ってる／知らない」を自己申告させる**
- **面談でテストしていない論点を、既習カードとして水増しする**（`known:` は「テストして答えられた」の記録であって、
  「たぶん知っているだろう」の記録ではない）
- 答えられなかったものに `known:` を付ける（出てこないカードになる）
- **ユーザーが正しさを確認できなかった裏面を残す**
- 棚卸しの途中で解説を始める（このスキルは診断であって授業ではない）
- 1 回の初期化で新規カードが 20 枚を超える
- 方針を書かずにカードだけ作る（基準が無いと以後の grill が判断できない）
- 承認なしで main にマージする
- `--worktree` で未承認のカードを push する
- `decks/` 以外のファイルを一緒にコミットする
