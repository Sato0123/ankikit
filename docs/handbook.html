      handbook

      その日の学習を掘り出して、
      Anki カードにするまで

      対話で振り返り、記憶に残す価値のある部分だけをカードにする。カードは Markdown で書き、main にマージされたものだけが Anki に入る。

      01 / SOURCE

      カードの正は decks/ 配下の Markdown。Anki へは片方向に流し込むだけで、Anki 側の編集は戻ってこない。直したいときは Markdown を直して push し直す。

      02 / APPROVAL

      承認の境界は git のマージ。ブランチ上で書いただけのカードは Anki に入らない。マージが承認そのもの。

      03 / PUSH

      ankikit push が読むのは作業ツリーではなく main の内容。「追加 0」と出たら、まだマージされていないということ。

      全体の流れ

      デッキを立ち上げるのは 1 デッキにつき 1 回（/anki-initialize）。あとは学習した日の終わりに毎回 /anki-grill を回す。下は grill の 6 ステップで、横断する帯が承認ライン。

      branch — ここまでは承認なしで進めてよい。Anki には 1 枚も入らない

      1. 1
        デッキの特定

        今日はどのデッキの話か決める。決まらないと「入れる基準」が決まらず質問が散る。該当デッキが無ければ /anki-initialize へ。

      2. 2
        振り返り（掘る）

        そのデッキの方針に沿って問い詰める。一度に一問。5〜15 往復。

      3. 3
        カード候補

        5〜10 枚を提案する。ユーザーが口にした表現をそのまま使う。

      4. 4
        staging ブランチで作成・コミット

        ankikit stage → decks/<slug>/cards/YYYY-MM-DD.md に書く → lint → コミット。

      承認 ＝ main へマージ この線を越えたものだけが Anki に入る uv run ankikit approve <slug>

      main — push が読むのはここだけ

      1. 5
        push

        uv run ankikit push --deck <slug>。「追加 N / 更新 M」が結果。

      2. 6
        Anki → AnkiWeb → スマホ

        PC 版 Anki に入り、同期でスマホに届く。

      手で書きたいときは decks/<slug>/cards/YYYY-MM-DD.md に直接足して、同じくマージしてから uv run ankikit push。経路が違っても承認ラインは同じ。

      セットアップ

      リポジトリは 2 つに分かれている。 道具は何度でも配れるが、カードはあなただけのもの。git の履歴は後から消せないので、混ぜない。

      public ankikitprivate anki-decks
      役割道具そのものあなたの記憶
      中身src/ankikit/ tests/ docs/ decks/README.md（記法の仕様）decks/<slug>/（カード本体） anki.toml .claude/skills/
      触る頻度たまに（道具を直すとき）毎日（振り返り）

      道具は uv add で入れる。カード側で uv run ankikit ... と打つ形は変わらない。 config.py の find_repo_root() がカレントから上へ anki.toml / decks/ を探すので、カード側のリポジトリに居れば環境変数は要らない。

      1. 1

        PC 版 Anki に AnkiConnect を入れる

        アドオンコード 2055492159。AnkiWeb のアドオンページから。

      2. 2

        カード用のリポジトリを作る

        mkdir ~/anki-decks && cd ~/anki-decks git init uv init --bare uv add "ankikit @ git+ssh://git@github.com/Sato0123/ankikit"

        道具を直しながら使うなら [tool.uv.sources] に ankikit = { path = "../Anki", editable = true } と書く。直したそばから反映される。

      3. 3

        スキルを配置する

        uv run ankikit install

        /anki-grill と /anki-initialize が .claude/skills/ に入る。スキルの正はパッケージの中（src/ankikit/skills/）なので、道具を更新したら install を叩き直すと最新になる。

        コマンド意味
        ankikit install配置する。既にあって内容が同じなら何もしない
        ankikit install --list何が入るかだけ見る
        ankikit install --force手で直したスキルも上書きする

        手で直したスキルは --force が無ければ上書きされない。意図せず自分の変更が消えないようにしてある。

      4. 4

        接続とノートタイプ名を確認する

        uv run ankikit doctor

        ノートタイプ名は Anki の UI 言語や導入経緯で変わる。NG が出たら anki.toml の [note_types] を直す。この環境の実測値は basic=基本［表面 / 裏面］、cloze=穴埋め問題［Text / 裏面追記］。

      5. 5

        最初のデッキを立ち上げる

        /anki-initialize を呼ぶ。方針と最初の 10〜20 枚までまとめて作る。

      場所を間違えると黙って 0 件にはならない。 decks/ が見つからないところで叩くと、どこを見たかを言ってエラーで止まる。

      skill

      /anki-grill — 学習した日の終わりに毎回

      ユーザーはスマホで 1 枚ずつ登録したくないし、観点を自分で列挙するのも面倒だと思っている。質問はこちらが出す。

      0. 下ごしらえ（黙ってやる。要約して見せない）

      • decks/README.md — 記法とコマンド
      • decks/*/README.md — 各デッキの目的・入れる基準・入れない基準・## 前提
      • 直近数日の decks/*/cards/*.md — 重複回避と「昨日のあれどうなった？」用
      • uv run ankikit decks — 未マージのカードが残っていたら、先に片付けるか聞く
      1. 1

        デッキの特定 — 振り返りより先

        既にデッキがあるなら、slug と目的を 1 行ずつ並べて選ばせる。

        今日はどれ？
        ・english-vocab — 会議で出た語彙
        ・sre — 障害対応で詰まったこと

        どのデッキにも当てはまらなければ新しいデッキを提案し、作成は /anki-initialize に任せる。ここで ankikit new を叩いて README を片手間に埋めない（後の全セッションの判断基準になる場所を雑に作らない）。

        1 セッション 1 デッキが基本。 話が複数デッキに散ったら、デッキごとにブランチを分けて 4〜6 を繰り返す。

      2. 2

        振り返り（掘る）

        デッキの「入れる基準」を頭に置いて掘り始める。最初の一言は短く。

        今日 sre まわりで何をやった？ 一番時間を使ったところから。

        鉄則

        • 一度に一問だけ。 まとめて 3 つ聞かない。
        • 答えを要約して返さない。 相槌もいらない。次の質問に進む。
        • 抽象語は許さない。「うまくいった」→ 何が、どうなって、前と何が違う？／「理解した」→ じゃあ説明して。3 行で。／「難しかった」→ どこで手が止まった？ 何分？ 最終的に何を見て解決した？
        • 「知ってる」には説明させる。 説明が詰まったら、そこが最高のカードになる。
        • 詰まった / 間違えた / 驚いた を最優先。 スムーズにできたことは記憶する価値が低い。
        • 手を動かしていない知識は、使う場面を聞いてから判断する。答えられないならカードにしない。
        • 5〜15 往復。

        切り口のストック（一本道が尽きたら）

        切り口問い
        失敗今日エラーになった / 想定と違った瞬間は？ 原因は結局なんだった？
        判断選ばなかった選択肢は？ なぜそっちを捨てた？
        境界それが使えないのはどういうとき？ 例外は？
        区別似てるけど違うものは？ 何が違う？
        再現明日同じことをゼロからやれる？ どこで詰まりそう？
        由来なぜそういう仕様 / 語法になっている？
        昨日前回のカードで、今日実際に出てきたものは？

        やめる合図

        • ユーザーが「もういい」「それくらい」と言った
        • 3 往復続けて新しい事実が出てこない
        • カード候補が 10 枚を超えた（1 セッション 5〜10 枚が適量）
      3. 3

        カード候補を出す

        会話全体から拾う。ユーザーが口にした表現をできるだけそのまま使う（自分の言葉のほうが思い出せる）。

        入れる

        • 今日詰まった・間違えた事実
        • 説明を求めたら詰まったこと
        • 「へえ」と言った箇所
        • 判断の根拠（なぜ A ではなく B か）

        入れない

        • デッキ README の「前提」に既にあること
        • 調べれば 10 秒で出るリファレンス
        • 一覧・手順の丸暗記
        • 文脈のない用語定義
        • 「明日使う場面」が答えられなかったもの
        • 既存カードと同じ表面

        カードの形

        • 1 カード 1 事実。「かつ」「および」が入ったら分割する。
        • 表面は想起のきっかけ。 用語ではなく、実際に遭遇する状況の形にする。
        • 裏面は一文 + なぜ。 理由が無いカードは忘れる。
        • 手続きや文章の穴埋めが向くなら {{c1::...}} を使う。
        • 出典メモは <!-- --> に書く（Anki には送られない）。
        表面
        悪いuseEffect の依存配列
        良いuseEffect の依存配列に空配列を渡すと、いつ再実行される？
      4. 4

        ブランチで作成・コミット

        ここまでは承認なしで進めてよい。ブランチの中身は Anki に影響しない。

        uv run ankikit stage <slug> # staging/<slug> に切り替え（無ければ main から作る） # decks/<slug>/cards/<YYYY-MM-DD>.md に書く（既にあれば末尾に追記。既存カードは触らない） uv run ankikit lint --deck <slug> git add decks/<slug> && git commit -m "cards(<slug>): <YYYY-MM-DD> N枚"

        エラー 0 件を確認してからコミットする。decks/ 配下だけを add する。

      5. 5

        承認（main へマージ）

        git diff main...HEAD -- decks/

        差分を見せて、承認を求める。

        staging/<slug> に N 枚コミットした。main にマージすると Anki に入る。マージしていい？

        明示的に承認されるまでマージしない。「消したい」「直したい」と言われたら、ブランチ上で直してコミットし直し、もう一度聞く。

        uv run ankikit approve <slug> # staging/<slug> を main に --no-ff マージし、main に切り替わる
      6. 6

        push

        uv run ankikit push --deck <slug>
        • 「追加 N / 更新 M」の行をそのまま報告する。
        • 「追加 0」なら、まだマージされていない。uv run ankikit pending で確認する。
        • Anki が起動していないと AnkiConnect に接続できません で落ちる。そのときはカードは main にマージ済みで無事だと伝え、「Anki を起動して uv run ankikit push」と案内する。ここで作業を巻き戻さない。
        • ノートタイプ名で失敗したら uv run ankikit doctor の結果を見せる。

        最後は 2〜3 行で締める。今日の枚数、どのデッキに入ったか、次に掘ると良さそうな残りの論点。長い総括は要らない。

      やらないこと

      • デッキを決めずに掘り始める
      • 質問を飛ばしていきなりカードを作る
      • 承認なしで main にマージする
      • --worktree で未承認のカードを push する
      • 1 セッションで 15 枚以上作る
      • ユーザーが言っていない知識を「補足」として勝手にカードにする
      • decks/ 以外のファイルを一緒にコミットする
      skill

      /anki-initialize — 新しいデッキを立ち上げる（1 デッキ 1 回）

      grill は「今日あったこと」を掘るが、initialize はまだ何も起きていない状態に骨組みを置く。だからこのスキルに限り、モデル側が論点と裏面を持ち込む。

      その代わりの歯止め

      • カードにするのはユーザーが答えられなかったものだけ
      • 裏面はモデルが書くが、1 枚ずつ正しさを確認させる

      承認境界は grill と同じ

      • main にマージされるまで Anki には 1 枚も入らない

      0. 下ごしらえ（黙ってやる）

      • decks/README.md — 記法とコマンド
      • decks/*/README.md を全部 — 似た目的のデッキがあれば、新設せずそこに足すことを先に提案する
      • uv run ankikit decks — 未マージが残っていたら先に片付けるか聞く
      1. 1

        スコープの確定

        デッキは「入れる基準が書ける粒度」でだけ切る。ここが決まらないと以後の全セッションの判断がぶれる。1 問ずつ聞く。

        何を覚えたい？ 具体的に。
        なぜ今？ 何をしていて必要になった？
        3 か月後、何ができていれば「作ってよかった」と言える？
        粒度例症状
        広すぎプログラミング 英語入れる基準が「役に立つこと」にしかならない。切り直す
        ちょうどreact-rendering sre-oncall meeting-english入れない基準を具体例で書ける
        狭すぎuseEffect の依存配列10 枚で尽きる。一段上げる

        決まったら slug（kebab-case）と Anki 上のデッキ名（親::子）を提案し、確認を取ってから作る。

        uv run ankikit new <slug> --anki-deck "親::子"

        new を先に実行すること。 ankikit stage は decks/<slug>/ が存在しないと失敗する。

      2. 2

        方針を仮置きする

        README をここで全部埋めない。 問診の軸になる分だけ決める。

        • 目的 — 1〜2 文。1 で聞いた「3 か月後」をそのまま使う
        • スコープ外 — 今回は扱わないもの（例: sre-oncall なら「Kubernetes の内部実装は扱わない」）

        入れる基準・入れない基準は 5 で確定させる。今書くと、実際に何を捨てたかを知らないまま「重要なことを入れる」のような使えない基準になる。

      3. 3

        棚卸し面談（このスキルの本体）

        目的は「知らないことの発見」であって、教えることではない。 ここで解説を始めない。

        1. スコープから論点を 15〜25 個立てる。リストはユーザーに見せない（見せると自己申告になり、一番危険な「知っているつもり」が素通りする）。
        2. 1 問ずつ口頭でテストする。 まとめて 3 つ出さない。
        3. 答えを聞いて 3 つに仕分ける。
        反応扱い
        即答できた捨てる。 5 の「前提」に記録する
        説明が詰まった・曖昧カード候補（最良の候補）
        「知らない」と即答カード候補。ただしスコープ内かを確認してから

        「知ってる」には必ず説明させる。 用語を言えるのは知っているうちに入らない。→「じゃあ説明して。3 行で。」

        論点の立て方（ストック）
        • 地雷: この分野を始めた人が最初の 1 か月で必ず踏む間違いは？
        • 区別: 似ていて混同されるペアは？ 何が違う？
        • 境界: それが使えないのはどういうときか。例外は？
        • 既定値: 何も指定しないとどうなるか
        • 由来: なぜそういう仕様 / 語法になっているか
        • 手順の落とし穴: 順番を間違えると壊れるところ
        • 本人固有: ユーザーの環境・仕事で、それが実際に出てくる形は？

        本人固有の論点を必ず混ぜる。 一般論だけで組むと教科書のコピーになり、思い出すきっかけにならない。

        やめる合図
        • カード候補が 20 に達した
        • 3 問続けて即答された → 論点が浅い。一段深くするか、スコープ自体を上げる
        • 3 問続けて「まったく知らない」 → 深すぎる。初期化ではなく学習が先。段を下げる
        • ユーザーが「もういい」と言った
      4. 4

        カード化

        答えられなかった問いだけをカードにする。即答できたものを「念のため」入れない。

        • 表面はユーザーが詰まった問いの形をそのまま使う
        • 裏面はモデルが書く。これはこのスキルだけの例外。 一文 ＋ なぜ
        • 1 カード 1 事実

        裏面の確認（省略しない）

        これで合ってる？ 違ってたら直して。
        • ユーザーが自分の環境の言葉で言い直したら、その言い方を採用する
        • 「正しいか判断できない」と言われたカードは作らない。 正しさを確認できないカードは毒で、間違ったまま何か月も復習することになる。捨てるか、調べてから次のセッションに回す

        書く場所は decks/<slug>/cards/<YYYY-MM-DD>.md。冒頭のフロントマターに出所を残すと、初期化のカードだけを Anki 側で後から絞り込める。

        --- tags: [seed] ---

        10〜20 枚。番号付きで表面と裏面をそのまま見せる。長い解説は要らない。

      5. 5

        方針を確定させる

        ここまでで「実際に何が弱かったか」が分かっている。decks/<slug>/README.md を書き切る。

        • 入れる基準 / 入れない基準は、このセッションで実際に拾った例・捨てた例を引いて書く。
          悪い:「重要なことを入れる」／良い:「即答できずに詰まった問いだけ。用語の定義だけのカードは入れない（今日 3 問捨てた）」
        • ## 前提（既に押さえていること） に、3 で即答できた論点を箇条書きで残す。以後の /anki-grill がこれを読み、同じことを二度と聞かない・カードにしない。
        • 運用メモ: 1 日の新規枚数の目安、次に掘る予定の領域
      6. 6

        ブランチでコミット（方針とカードを分ける）

        uv run ankikit stage <slug> uv run ankikit lint --deck <slug> git add decks/<slug>/README.md && git commit -m "deck(<slug>): 方針" git add decks/<slug>/cards && git commit -m "cards(<slug>): <YYYY-MM-DD> N枚（初期）"

        分けておくと、承認時に「方針」と「カード」を別々に確認できる。

      7. 7

        承認（main へマージ）

        git diff main...HEAD -- decks/
        staging/<slug> に方針と N 枚をコミットした。main にマージすると Anki に入る。マージしていい？

        「この枚は要らない」と言われたら、ブランチ上で消してコミットし直し、もう一度聞く。承認されたら uv run ankikit approve <slug>。

      8. 8

        push

        uv run ankikit push --deck <slug>

        最後は 2〜3 行。デッキ名、枚数、次に掘ると良さそうな領域。総括は要らない。

      やらないこと

      • スコープを決めずに論点を出す
      • 論点リストを見せて「知ってる / 知らない」を自己申告させる
      • ユーザーが即答できたことをカードにする
      • ユーザーが正しさを確認できなかった裏面を残す
      • 棚卸しの途中で解説を始める（診断であって授業ではない）
      • 1 回の初期化で 20 枚を超える
      • 方針を書かずにカードだけ作る
      • 承認なしで main にマージする
      • --worktree で未承認のカードを push する

      カードの書き方

      デッキ 1 つ = ディレクトリ 1 つ。ここがカードの正で、Anki には片方向に流し込む。Anki 側で直接編集した内容は戻ってこないので、直したいときはこのファイルを直して push し直す。

      decks/ english-vocab/ README.md ← このデッキの方針（フロントマターが設定になる） cards/ 2026-08-20.md ← その日に足したカード 2026-08-21.md

      デッキ README.md

      フロントマターが設定、本文が方針。方針の本文は /anki-grill が読んで「何をカードにするか」を判断する材料になるので、入れる基準と入れない基準は具体的に書く。

      --- anki_deck: "英語::語彙" # Anki 上の実デッキ名。:: で階層。省略時はディレクトリ名 note_type: basic # basic | cloze（カード側に {{c1::}} があれば自動で cloze） tags: [english] # このデッキの全カードに付くタグ --- ## 目的 ## 入れる基準 ## 入れない基準 ## 前提（既に押さえていること） ## カードの作り方 ## 運用メモ

      ## 前提 は /anki-initialize の棚卸しで即答できた論点を残す場所。/anki-grill がこれを読んで、既に押さえていることを二度と聞かない・カードにしないための基準になる。

      雛形は uv run ankikit new <slug> --anki-deck "英語::語彙" で作れるが、新しいデッキは /anki-initialize から始めるのが本筋（方針と最初の 10〜20 枚をまとめて作る）。

      カードファイル（cards/YYYY-MM-DD.md）

      --- tags: [meeting] # このファイル内の全カードに付くタグ（省略可） --- ## Q: circle back A: 後で改めて議論する <!-- 出典: 今日のMTGで上司が使った --> ## {{c1::defer}} to someone A: 人の判断に従う / 一任する tags: nuance
      記法意味
      ## 行カードの開始。行頭の Q: は飾りなので取り除かれる
      A: 行ここから裏面。次の ## か EOF まで（複数行可）
      tags: 行そのカード固有のタグ。空白かカンマ区切り
      <!-- ... -->ファイル内のメモ。Anki には送られない。カードに残したいなら A: の本文に書く
      {{c1::...}}表面に含めると穴埋めカードになる

      書式チェックは uv run ankikit lint。

      重複と更新

      同一カードかどうかは表面のハッシュで判定し、Anki 側には ankikit-uid::<hash> タグが付く。

      直した場所push したときの挙動
      裏面だけ既存カードを更新（学習履歴は維持される）
      表面別カードとして追加される。古い方は Anki に残るので手で消す
      同じ表面を 2 回lint がエラーにする

      フィールドは HTML なので、改行は to_html() で <br> に変換してから送る。行頭の空白は落とされる。

      英単語 — JSON から一気に流し込む

      english-vocab デッキだけは対話も承認面談も通さない。本から拾った単語に「今日どこで詰まった？」と聞く意味は無いので、自分で JSON に打ち込んで ankikit eng に食わせる。検証・重複除外・decks/ への追記・コミット・Anki への反映まで 1 コマンドで走る。

      uv run ankikit eng words.json # 検証 → 重複除外 → 追記 → コミット → Anki uv run ankikit eng words.json --dry-run # 何が登録され何が弾かれるかだけ見る uv run ankikit eng words.json --tag duo3 # 全カードに出典タグを付ける

      承認の原則は形を変えて残っている。eng は main 上でしか push しないので、「Anki にあるもの = main にあるもの」は崩れない。他のブランチで書くだけなら --no-push。

      入力 JSON

      本から手で打ち込む前提の形式。配列だけでも、設定つきのオブジェクトでも受ける。

      { "tags": ["duo3"], # 全カードに付くタグ（省略可） "words": [ {"word": "anyway", "sentence": "Let's try anyway.", "meaning": "とにかく"}, {"word": "circle back", "sentence": "She circled back to me.", "note": "p.42"}, {"word": "wake", "sentence": "I ____ up early.", "meaning": "目を覚ます"} ] }
      キー意味
      word / 単語必須。覚えたい語。空欄の答えになる
      sentence / 例文必須。出会った文をそのまま。____ を書けばそこが空欄、書かなければ word を文中から探す
      meaning / 意味日本語の訳。省略可
      note / メモ出典ページや語法メモ。省略可

      できあがるカード

      ## Let's try ____. # 表面 = 例文の該当語を空欄にしたもの A: anyway # 裏面 = 単語 / 意味 / 完全な例文 / メモ とにかく Let's try anyway. tags: word::anyway # ← 重複判定のキー。消すと同じ単語が二重に入る

      目標は「anyway = とにかく」を思い出すことではなく、文の中の穴を埋められるようになること。だから表面は単語ではなく例文になっている。

      空欄化のルール

      入力どうなるか
      例文に ____ があるそこが空欄。不規則変化（wake → woke）はこれで書く
      そのままの語があるその語を空欄にする。大小は無視（Anyway も可）
      素直な語形変化circle → circled、stop → stopped 程度までは追う
      見つからないその 1 件だけエラー。答えが表面に見えるカードは作らない

      重複と壊れた入力

      重複判定はこのデッキだけ単語で行う（他のデッキは表面のハッシュ）。Circle Back と circle-back は同じ語として扱う。

      1 件の不備で全体は止まらない。壊れた行と重複だけ落として、残りはそのまま登録する。だから同じファイルに追記しながら何度流してもよく、直した行だけが後から入る。全部止めたいときは --strict。

      ERROR [5] woke: 例文に 'woke' が見つからないので空欄にできません。… ERROR [6] defer: sentence が空です 重複: [4] Anyway: ファイル内の [1] と同じ単語なので飛ばしました english-vocab → 英語::語彙: 入力 7 件 / 登録 4 / 重複 1 / 不備 2
      終了コード意味
      0全件そのまま登録できた
      1登録はしたが、飛ばした行がある
      21 枚も作れない（ファイルが無い / JSON が壊れている / Anki が起動していない）

      JSON が壊れていたら行・桁とその行の中身を出す。全角の ： や末尾の余分なカンマといった手打ちの定番はヒントまで出る。

      何を入れるか

      入れる

      • 読んでいて意味が取れずに止まった語
      • 意味は知っていたが、その文での使われ方が意外だった語
      • 例文が本文からそのまま取れる語（自作の例文より、出会った文を使う）

      入れない

      • 例文なしの単語（この形式に載らない）
      • 固有名詞、専門用語そのもの
      • 既にこのデッキにある語（word:: タグで自動的に弾かれる）

      1 ファイル 20〜40 語くらいが読み返しやすい。本の章ごとに分け、--tag duo3 のように出典をタグに入れておくと後で絞り込める。

      コマンド

      コマンド名は ankikit。グローバルの ~/.local/bin/anki は別ツールなので混同しない。

      承認フロー（この順に叩く）

      uv run ankikit stage <slug> # staging/<slug> に切り替え（無ければ main から作る） # → decks/<slug>/cards/YYYY-MM-DD.md を書く uv run ankikit lint --deck <slug> # 書式チェック git add decks/<slug> && git commit -m "cards(<slug>): YYYY-MM-DD N枚" git diff main...HEAD -- decks/ # 承認前の確認 uv run ankikit approve <slug> # main へ --no-ff マージ ＝ 承認 uv run ankikit push --deck <slug> # ここで初めて Anki に入る

      一覧

      コマンド用途
      ankikit decksデッキ一覧・枚数・未マージ枚数
      ankikit new <slug>デッキの雛形作成
      ankikit stage <slug>デッキ用の staging ブランチに切り替え
      ankikit lint書式チェック（作業ツリー）
      ankikit pendingまだ main にマージされていないカード
      ankikit approve <slug>staging を main にマージ（＝承認）
      ankikit push --dry-run何が追加・更新されるか確認
      ankikit push --deck <slug>反映（main の内容のみ・Anki 起動が必要）
      ankikit eng <file.json>英単語 JSON をカードにして Anki まで反映（詳細）
      ankikit installスキル（/anki-grill・/anki-initialize）をこのリポジトリに配置（詳細）
      ankikit doctorAnki 接続とノートタイプ名の確認
      uv run pytestテスト（道具側のリポジトリで）

      --ref <branch> で承認済みとみなすブランチを変えられる。push --worktree は承認を無視して作業ツリーを送る非常口。通常は使わない。

      リポジトリを触る

      道具（public ankikit）とカード（private anki-decks）で置き場が分かれている。どちらに何があるかを先に押さえる。

      道具側 — public ankikit

      パス役割
      src/ankikit/ライブラリ層（parser → deck → sync → connect、承認判定は approval）
      src/ankikit/vocab.py英単語 JSON の検証・例文の空欄化・重複キー（ankikit eng の中身）
      src/ankikit/commands/サブコマンド 1 つ = 1 モジュール。cli.py は組み立てるだけ
      src/ankikit/skills/スキルの正。ankikit install がここからカード側へ配る
      decks/README.mdカードファイルの記法（カードそのものではなく仕様）
      docs/handbook.htmlこのページ。build_pages.py が包んで GitHub Pages へ
      tests/pytest。uv run pytest

      カード側 — private anki-decks

      パス役割
      decks/<slug>/README.mdそのデッキの方針。「入れる基準／入れない基準」が判断材料
      decks/<slug>/cards/YYYY-MM-DD.mdカード本体
      anki.tomlAnki 環境依存の設定（ノートタイプ名・フィールド名）
      .claude/skills/ankikit install が置く。手で直すなら --force の挙動に注意
      pyproject.tomlankikit への依存だけ。uv.lock でバージョンが固定される

      サブコマンドを足す

      commands/ にファイルを 1 つ作り（NAME / HELP / add_arguments(parser) / run(args) -> int）、commands/__init__.py の ALL に並べる。cli.py は触らない。

      decks/ が無くても走るコマンド（new install doctor）は NEEDS_DECKS = False を置く。既定は True で、decks/ が見つからなければ cli が理由を出して止める。

      実装上の注意

      • カードの置き場は config.find_repo_root() が決める。 環境変数 ANKI_REPO_ROOT → カレントから上へ anki.toml / decks/ を探す → 開発時のパッケージ 2 つ上、の順。依存として入れると 3 番目は site-packages を指すので当てにできない。
      • approval.decks_at(ref) が git archive で ref 時点の decks/ を一時展開する。push はそこを読む。一時ディレクトリなので、カードの読み込みは必ず with の中で終わらせる。
      • 同一カード判定は表面のハッシュ（ankikit-uid::<hash> タグ）。ただし english-vocab だけは単語（word::<単語> タグ）。
      • ノートタイプ名は Anki の UI 言語で変わる。config.py の DEFAULTS が既定値で、anki.toml の [note_types] が項目単位で上書きする。ankikit doctor で確認する。
      • フィールドは HTML。改行は to_html() で <br> に変換してから送る。行頭の空白は落とされる。
      • ANKI_CONNECT_URL で接続先を差し替えられる。

      anki.toml（英語 UI の場合）

      [note_types.basic] model = "Basic" front = "Front" back = "Back" [note_types.cloze] model = "Cloze" front = "Text" back = "Back Extra"

      Anki 本体リファレンス

      Anki の構造は 4 層に分かれ、設定もこの階層ごとに存在する。デッキ自体は学習アルゴリズムの数値をほぼ持たない——それはデッキオプション（プリセット）が保持し、複数デッキで共有できる。

      デッキ (Deck) カードの置き場 └─ カード (Card) ノートタイプのテンプレートから自動生成 └─ ノート (Note) フィールドにデータが入っている実体 └─ ノートタイプ (Note Type / Model) フィールド定義＋カードテンプレート定義

      実践的な設定の勘所

      1. アルゴリズムは FSRS 推奨。 Deck Options の一番下で ON。目標保持率 90% から始め、レビュー 1000 件を超えたら Optimize で個人最適化。
      2. 学習ステップは 1 日以内に収める。 FSRS 導入後は長い学習ステップは非推奨（1m 10m 程度で十分）。
      3. 1 日の新規カード枚数は少なめから。 10〜20 枚 / 日で始め、こなせるようなら増やす。
      4. Maximum reviews/day は絞りすぎない。 低いと復習が繰り越されて雪だるま式に増える「隠れ滞留」を招く。
      5. プリセットは目的別に複数用意。 性質の違うデッキは別プリセットにする。
      6. フラグ・タグは学習順序に影響しない。 優先度を変えたいときは Reposition か フィルタデッキ。

      各層の設定

      デッキオプション（プリセット）

      歯車アイコン → Options。1 つのプリセットを複数デッキに割り当てられるのがポイント。

      グループ主な項目
      Daily LimitsNew cards/day（新規導入の上限）／ Maximum reviews/day（詰まり防止に大きめ推奨）／ 親子デッキ間で上限をどう共有するか
      New CardsLearning steps（例 1m 10m）／ Order（追加順・ランダム）／ Insertion order
      LapsesRelearning steps ／ Leech action（サスペンド or タグのみ）／ Leech threshold ／ Minimum interval
      Display OrderNew/review order ／ Interday・Intraday learning order ／（FSRS 時）Ascending retrievability
      Burying同じノートから生成された兄弟カードの重複出題を抑制（new / review / interday）
      Timer・Audio解答時間の表示 ／ 自動再生・スキップ動作
      FSRS有効化（グローバル）／ Desired retention（0.70〜0.97、目安 90%）／ FSRS parameters（Optimize で個人最適化）／ Maximum interval ／ Historical retention
      SM-2 専用Starting ease ／ Easy bonus ／ Interval modifier ／ Graduating interval ／ Easy interval（FSRS 有効時は非表示）
      Easy Days曜日ごとに Normal / Reduced / Minimum。間隔計算後の微調整で、過去には遡及しない
      ノートタイプ（Note Type / Model）

      「Manage Note Types」から管理。フィールド構成とカードテンプレートのセットであり、デッキとは独立した概念（同じノートタイプを異なるデッキで使い回せる）。

      • フィールド: 名前・並び順、表示フォント、Sticky（次の追加時に内容を保持）、Sort field（並び替え・重複チェックの基準）
      • カードテンプレート: Front / Back Template（{{フィールド名}} で挿入、{{FrontSide}} で表面を引き継ぎ）、Styling (CSS)、条件付き表示 {{#フィールド}}...{{/フィールド}}
      • 1 つのノートタイプから複数枚のカードを自動生成できる（単語→意味 / 意味→単語）
      • 特殊: Cloze（{{c1::語句}}）／ Basic (and reversed card) ／ Image Occlusion
      • Change Note Type: 既存ノートをフィールド対応させながら別ノートタイプへ移行
      カードの状態とメタ値
      状態説明
      New未学習
      Learning / Relearning学習中・再学習中（短期間隔）
      Review卒業後、長期間隔で復習中
      Suspended一時停止（出題対象外）
      Buriedその日だけ非表示
      • メタ値: Due ／ Interval ／ Ease factor（SM-2）・Stability / Difficulty（FSRS）／ Reps・Lapses ／ Flag ／ Tags
      • 操作: Forget（New に戻す）／ Set Due Date ／ Reposition ／ Find & Replace
      フィルタデッキ・全体設定

      フィルタデッキは検索条件でカードを一時的に集める特殊デッキ（例 is:due tag:英単語）。「Reschedule based on my answers in this deck」のチェックを外すと、元のスケジュールに影響を与えず一時演習だけできる。

      全体設定 (Preferences): Scheduler v3 ／ Next day starts at（日付の切り替わり時刻）／ Show next review time ／ AnkiWeb 同期 ／ バックアップ世代数 ／ 表示設定。
